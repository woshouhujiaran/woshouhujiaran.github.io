大模型微调学习笔记：从 SFT、DPO 到 RL，什么时候值得训练

发表于2026-10-22|更新于2026-10-22|分享
|浏览量:

假设要给一家商店做售后助手。用户发来一句话：

昨天收到的键盘有一个按键失灵，能直接换一台吗？

通用模型大概知道应该怎样回复：询问订单，了解故障，再解释换货流程。但把它接进业务系统之后，要求会具体得多。

它需要找到对应订单，查询当前换货规则，把处理结果写成系统能读取的格式；信息不足时要继续询问，涉及真正提交换货申请时，还得遵守确认与权限要求。

这时，几种看起来相似的问题就出现了：不知道最新规则，应该补文档还是训练？知道要查订单，却时常跳过这一步，应该怎样处理？两种回复都没有事实错误，业务却更认可其中一种，又该怎么教？

SFT、RLHF、DPO 和 RL，分别从不同的训练信号出发处理这些问题。先把一次任务里的困难拆开，再看这些名字，会比挨个背定义容易得多。

下面的商店、对话、字段与流程都是为讲解设计的例子，不代表真实项目或实测结果。本文讨论概念与工程选择，不展开具体训练框架和损失函数推导。

一、先看助手缺的是哪一块

用户说键盘坏了，助手回答“收货十五天内都能换”。如果商店当前的规则并非如此，问题首先在于事实依据。

RAG（检索增强生成）的做法，是先从外部资料中检索相关内容，再交给模型组织回答。规则文档更新后，需要更新索引，并确保检索能取到有效版本。订单状态、库存、价格这类实时信息，则更适合通过工具查询。

换一种情况：最新规则和订单查询工具都已经提供，助手还是偶尔不查订单就承诺换货。这时缺少的不是一条知识，而是执行流程的稳定性。

还可以再区分一种：两个回答都要求补充订单号，一个直接写“提供订单号”，另一个先回应用户遇到的故障，再说明查询原因。哪一种更适合商店的服务口径，涉及回答偏好。

观察到的问题 先尝试的处理方式 希望改变什么
没说清格式、语气、回答顺序 Prompt，也就是提示词与任务说明 当前任务的要求
缺少最新规则或订单信息 RAG、工具查询 回答可依据的事实
知道要求，却经常漏字段、跳步骤 检查提示与流程后，考虑 SFT 反复出现的行为模式
多种回答都可用，但有明确取舍 DPO 或 RLHF 回答之间的偏好
要根据执行结果改进一串动作 有可靠环境反馈时考虑 RL 多步任务中的决策

这张表给的是排查方向。一次售后任务完全可以同时用到提示词、检索、工具和训练过的模型，不必从中只选一个。

先试 Prompt 的原因也很实际。要求补充订单号、先给结论再解释、按 JSON 输出、不确定时说明缺少什么证据，都可以先写进任务说明，并提供少量示例。若这样已经能稳定达到目标，继续训练就要承担额外的数据清洗、版本管理、评测、部署和回滚成本。

只有在同一类高频任务里，提示词越来越长、修改一处容易影响另一处，而且仍有稳定性问题时，训练才有进一步比较的意义。业务流程和话术还在频繁变化时，也可以先用配置与规则引擎承接变化，等任务边界稳定后再判断。

二、SFT：把期望行为做成示范

SFT 的全称是 Supervised Fine-Tuning，中文叫监督微调。它在已有模型的基础上，用输入与期望输出组成的样本继续训练，调整模型参数，让模型更容易产生类似示范的输出。

有了这样的样本，SFT 才有机会把“先查询，再判断”的流程学进去。只拿一批最终回复去训练，不能据此认定模型已经学会了中间的工具决策。

SFT 可以用一致的示范来改善这种稳定性，也能帮助模型学习工单分类、标签抽取、工具调用格式，以及行业或品牌的表达口径。比如拒绝某项申请时，说明缺少的条件和可继续办理的路径，通常比生硬地回复“不行”更有帮助。

不过，模型倾向于生成正确格式，和系统保证格式正确，是两个层次。程序仍要验证输入输出。若输出带有置信度字段，也不能因为数字看起来精确，就把它当成已经校准过的可靠概率。

为什么不把整本售后手册都训进去？

假设商店调整了换货期限。通过文档和工具查询，能够让回答依据当前规则；如果依赖模型参数里记住的旧条款，就要处理知识更新与旧答案残留的问题。

因此，在这个场景里，更合理的分工是：用示范训练“先查规则、再据此判断”的习惯，把具体条款留在可更新、可追溯的外部系统中。

这不是说 SFT 完全学不到知识，而是说，对经常变化又需要核对出处的事实，把参数当成唯一存储位置，维护代价很高。

还有一种用途：让小模型接住固定任务

售后系统里的请求并不都需要最强模型。意图分类、固定字段抽取、简单流程回复，可以先让大模型生成候选示范，经过审核与清洗后，用来训练较小的模型。

如果小模型在这些明确任务上达到要求，就可以承担相应流量；复杂、含糊或超出范围的问题，再交给更强的模型或人工处理。这与模型蒸馏的思路相近：把较强模型的一部分任务表现迁移给较小模型。

这里比较的目标是，在质量要求下能否降低成本与延迟。小模型是否划算，还取决于部署方式、请求规模、路由效果和维护投入，不能只凭参数量下结论。

三、RLHF：先比较答案，再学习偏好

再看两条回复。它们都没有承诺一定能换货，也都要求补充订单号：

如果商店更希望先回应用户遇到的问题，再收集信息，就可以把 B 标为更受偏好的回答。换一个要求快速查询状态的场景，简洁的 A 也可能更合适。

这种比较可以涉及礼貌与直接、简洁与完整、先解释还是先给结论、何时转人工，以及拒绝请求后是否提供可行的替代方案。它既包含表达选择，也可能包含事实与流程质量，标注标准需要说清适用条件。

RLHF（Reinforcement Learning from Human Feedback）叫基于人类反馈的强化学习。以常见的“奖励模型加 PPO”路线为例，训练过程可以拆成下面几步：

  1. 先得到一个能够完成基本任务的模型，通常会经过 SFT。
  2. 对同一个问题生成多个候选回答。
  3. 让标注者按照统一标准比较回答，收集偏好数据。
  4. 用这些比较结果训练奖励模型，也就是 Reward Model，让它估计回答的受偏好程度。
  5. 让待优化模型生成回答，根据奖励信号更新参数，并持续评测。

这里多了一个中间环节：人工不必为训练中的每条新回答实时打分，而是先把偏好交给奖励模型学习，再由它提供训练信号。

与 SFT 相比，区别在于监督信息的组织方式。SFT 给出要学习的示范；偏好训练还显式利用“同一道题里，为什么更认可这一条”的比较关系。两者可以结合，并不意味着 SFT 无法学习风格，或偏好训练只处理语气。

PPO 在这里负责什么？

PPO 的全称是 Proximal Policy Optimization，通常译作近端策略优化。它是一种强化学习优化算法。在上面的流程中，它负责利用奖励反馈更新模型；它不是偏好数据，也不是人工标注方式。

问题在于，奖励模型给出的分数只是对真实目标的近似。假如它把“回答很长”误认为“服务很周到”，待训练模型就可能学会不断补充客套话，分数提高了，用户找答案却更费劲。这类利用奖励缺陷取得高分的现象，通常称为奖励黑客。

PPO 会约束相邻训练步骤的策略更新幅度。大模型的传统 RLHF 流程还常加入 KL 约束，用来衡量并限制当前模型与参考模型的输出分布差异，避免为了分数过度偏离原有行为。

这两种约束不宜混为一谈：限制一次更新的变化，与限制相对参考模型的偏离，关注的对象不同。它们都不能保证奖励设计正确，也不能保证原有能力绝不退化，仍然需要检查奖励模型的偏差和模型的实际表现。

四、DPO：能否直接用比较结果训练？

前面的流程需要训练奖励模型，再进行强化学习优化。奖励模型有没有学偏、PPO 的更新是否稳定、KL 约束强度怎样设置，都会增加训练与调试负担。

既然已经知道同一问题下 B 比 A 更合适，能不能直接利用这个比较关系？

DPO（Direct Preference Optimization），也就是直接偏好优化，采用的正是这条思路。数据通常包含一个问题，以及被偏好的回答 chosen 和相对不受偏好的回答 rejected。它直接用偏好对构造训练目标，不必另行训练一个显式的奖励模型，也不必采用传统的 PPO 优化流程。

“更偏向 chosen”描述的是训练方向，不保证每一条样本训练后都会在所有场景中得到同样变化。DPO 也不是把 rejected 丢掉、只拿 chosen 再做一遍普通 SFT；两条回答之间的比较信息参与了优化。

比较项 传统奖励模型与 PPO 路线 常见的离线 DPO 流程
偏好怎样进入训练 先训练奖励模型，再用奖励优化策略 直接使用偏好对构造训练目标
是否单独训练奖励模型 通常需要 不需要显式的独立奖励模型
主要工程负担 奖励模型、生成采样、策略优化与约束调节 偏好数据整理与偏好优化训练
需要重点检查 奖励偏差、优化稳定性、能力退化 标注一致性、数据覆盖、训练后泛化

DPO 减少了训练环节，因此有机会降低工程成本和调试难度。但“流程更简单”不能直接推成“效果一定更好”或“任何数据都能稳定训练”。

如果一批标注偏好简短，另一批却不分场景地偏好长回答，模型得到的信号就可能相互冲突。客服回复、合规表达、简洁程度，以及正确与错误的工具调用轨迹，都可以组织成偏好数据，前提是比较标准清楚、样本可信。

这里的“传统 RLHF”特指前面介绍的奖励模型与强化学习流程。更宽泛地讨论人类偏好对齐时，DPO 和 RLHF 的用词范围可能不同，不应因此把它们当成完全无关的两类目标。

五、RL：把反馈从“回复得好不好”延伸到“事情办得怎样”

RL 是 Reinforcement Learning，强化学习。它关注模型如何根据奖励反馈改进决策。RLHF 中的反馈与人类偏好有关，而更广义的 RL 不要求奖励一定来自人工比较。

在售后例子里，助手若只负责生成一段回复，评价对象主要是文本；如果它还要查订单、查规则、选择下一步工具，甚至准备提交申请，它就成了需要与环境交互的 Agent，也就是能围绕目标连续采取动作的智能体。

这条链路里，每一步都可能出问题：选错工具、参数不合法、检索策略没有找到有效条款、尚未查清就下结论，或者在不满足条件时调用了写入工具。

如果环境能够记录这些结果，就有机会把执行反馈用于训练。例如，查询工具调用成功、参数合法、最终处理正确，可以成为反馈的一部分；无效调用、错误承诺和越权动作，则需要被识别出来。

代码生成中的编译与单元测试、数学题的答案验证、检索是否命中目标证据，也提供了相对明确的反馈。因此，RL 不只是改善聊天语气，还可以用于优化任务完成过程。

有了分数，还要检查分数是否代表目标

假设把“最后提交了换货申请”视为唯一成功条件，助手可能为了完成任务而跳过必要核对。反过来，如果只奖励“没有发生错误”，一个总是拒绝办理的助手，也可能显得很安全。

所以设计反馈前，要先说清楚：什么叫正确完成，哪些情况本来就应该停止或转人工，中间步骤怎样评价，工具失败怎样归因，以及怎样发现模型在利用评分漏洞。

任务完成率、工具调用成功率、参数合法率、需要确认时的确认行为、人工接管情况，都可以提供观察角度，但不能脱离条件机械地奖励。人工接管率下降，可能是模型更可靠，也可能是它把该转交的问题强行处理了；确认次数增加，也可能只是重复打扰用户。

同样，单元测试通过只说明通过了现有测试，工具返回成功只说明接口执行成功，都不等于真实目标已经完全满足。反馈越可靠，训练越有依据；“能给一个数字”本身还不够。

静态偏好对为什么不能包办多步决策？

一条正确工具轨迹，可以作为 SFT 示范，也可以和错误轨迹组成 DPO 偏好对。但实际运行时，订单可能查不到，库存可能变化，某个接口也可能暂时失败。

静态数据能够教会模型已有案例中的选择，却不能代替它在新环境状态下的执行与验证。任务如果高度依赖连续交互，就需要把环境、奖励、离线评测与线上反馈连接起来，观察策略有没有退化。

这也是为什么不能只因为业务使用了 Agent，就直接决定做 RL。没有可靠环境、明确的成功判定和持续评估，训练结果很难解释。

六、模型学会了流程，系统仍要守住执行边界

假设助手已经经过训练，通常会在提交换货前询问用户。某一次，它仍然错误地产生了提交申请的工具调用，应该怎么办？

真正执行操作的服务，必须能够独立拒绝不满足条件的请求。训练改善的是模型行为的概率，权限与业务规则要由系统落实。

以售后申请为例，可以把各层职责对应起来：

系统机制 在这个例子中解决的问题
权限控制 当前用户是否有权操作这笔订单
二次确认 用户是否同意本次具体申请内容
审批流程 超过自动处理边界的申请由谁审核
幂等机制 请求重试时避免重复创建申请
回滚或补偿机制 执行失败或发现错误后怎样恢复
操作日志 保留调用、依据与结果，便于追查

同样的分工也适用于删除数据、发送邮件等有实际后果的动作。SFT、RLHF 或 RL 可以帮助模型更经常做出合适选择，但不能替代执行层的校验与拦截。

七、基模升级后，原来的微调还值不值得留？

现在可以回到一个常见问题：既然通用基模越来越强，专门做的微调会不会很快失去收益？

先看它原本补了什么。如果只用一批普通问答改善通用知识，后续基模升级可能就覆盖了这部分提升。此时还要维持自有数据、训练与部署流程，未必划算。

如果所谓提升只是“说话更像客服”，却没有固定评测、线上指标和错误归因，就连新基模是否已经达到同样效果，都很难判断。

还有一种情况更容易被忽略：微调本身可能损害表现。历史客服记录中可能混着旧条款、错误流程、不合适的话术、随意承诺和用户隐私。把这些记录直接作为标准答案，相当于把历史问题也交给模型学习。样本增加不自动等于质量提高，训练前需要先做纠错、更新、去冲突和隐私处理。

相较之下，值得持续比较的价值往往来自更具体的业务要求：字段和工具格式是否稳定，流程是否能重复执行，话术是否符合约定，复杂情况是否正确转交，以及能否用较小模型承接固定任务。

基模升级不一定自动满足这些要求，也不保证原有训练方案永远必要。更合适的做法是，把新基模加上合理的提示、检索和工具配置，作为新的候选方案，与原来的微调系统重新比较。

如果任务边界仍在变、数据还很脏、没有评测集，或者反馈只能描述成“感觉好一些”，就先把这些基础工作补齐。训练的价值需要能被验证，使用了哪种算法不能替代这个判断。

八、用什么证据判断训练有收益

在训练开始前，就应该准备核心场景测试集、已知失败案例、安全边界测试和格式稳定性测试，并定义上线后怎样观察效果。它们用于评价模型，不能只拿训练样本充当验证结果。

对售后助手来说，测试不应只有“提供完整订单信息后顺利换货”。还要包含缺订单号、订单不存在、规则不支持、工具超时、用户撤回申请，以及不允许操作他人订单等情况。

指标要覆盖整条任务链

观察维度 可以检查的指标 需要结合什么理解
任务效果 分类准确率、抽取 F1、工具调用成功率、JSON 合法率、任务完成率、用户问题解决率 格式正确是否同时意味着业务判断正确
回答质量 幻觉率、无证据回答率、格式错误率、拒答准确率、低置信度处理情况、人工接管率 有无依据，以及该继续、该拒绝、该转交时是否处理得当
成本与速度 单次调用成本、延迟、小模型承接流量、大模型调用量 是否在相近质量要求下比较，并计入训练与维护投入
风险 越权动作率、错误拒答率、错误放行率、审批触发率、回滚次数、投诉率 风险事件是否减少，正常任务是否被过度阻断

F1 是信息抽取中综合考虑准确性与覆盖情况的一种指标：只抽出很少但很准的信息，与抽出很多却夹杂错误的信息，都需要一起衡量。具体选什么指标，还是要对应系统实际承担的任务。

JSON 合法率尤其容易被误读。它回答“能不能解析”，而不是“该不该办理换货”。同样，用户满意也不能独自证明系统可靠：一个随意承诺补偿的助手，可能暂时得到好评，却增加错误放行和投诉风险。

看一次演示，和证明收益，差在哪里

下面只是设计评估时的演示，不是实际测试数据。

假设比较“基模加提示词”和“经过 SFT 的模型”，两者使用相同工具、规则资料与测试任务。先记录各自在哪些案例中漏字段、跳步骤或错误转交，再看训练后是否减少这些问题，同时检查原本能完成的任务有没有退化。

如果只挑几条效果好的回复展示，无法知道变化是否普遍；如果训练版拿到了更新的规则文档，基线却没有，也无法把提升归因于微调。

基模、Prompt、RAG、工具或模型版本发生变化后，都要跑稳定的回归集。分类表现提高，但工具参数更容易填错，仍然可能让整个系统变差。

上线后还要继续验证

离线评测通过后，可以先灰度发布，让少量真实请求进入新版本；条件允许时进行 A/B 测试，在可比较的流量中观察两个版本。

上线监控需要继续看幻觉、格式错误、人工接管、投诉、成本与延迟，也要检查权限、确认和审批等边界。保留可回滚版本，明确什么情况触发回滚，才能在指标退化时及时处理。

因此，微调的交付结果不只是一个模型文件，还包括它与哪版提示、规则、工具共同通过了哪些验证，以及上线后怎样继续检查。

九、把训练方法放回业务判断中

再看最初那句“键盘按键失灵，能直接换一台吗”，现在可以按问题出现的位置逐步处理了。

缺事实，就让助手取得当前规则与订单依据；要求没有交代清楚，就先调整提示和示例；任务要求明确，却反复出现相同的流程或格式错误，再用高质量示范评估 SFT 的收益。

当主要困难变成多种合格回复之间的取舍，可以整理一致的偏好标准，比较 DPO 或传统 RLHF 路线。如果还需要根据执行结果改善连续动作，则进一步检查环境反馈是否可靠、任务是否适合 RL，以及系统执行边界是否已经落实。

这些方法连起来，说明一个实际判断：是否训练，取决于哪类错误持续发生，以及什么反馈能够证明它被改善。 基模升级以后，也应该沿着这条任务链重新评估。原来用训练补的能力，可能已能用更简单的方式得到；仍未满足的稳定性、偏好和成本要求，则继续成为定制优化的依据。
